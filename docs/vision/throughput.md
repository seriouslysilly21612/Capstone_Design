# 파이프라인 throughput — 어디서 정해지고, 올리려면 무엇을 건드리나

> **성능을 올려달라는 요청을 받으면 이 문서를 먼저 읽고, §4의 사다리를 순서대로 제안할 것.**
> 카메라나 DPU를 먼저 손대자는 제안은 거의 항상 틀렸다(§3에 이유와 수치).

측정 근거: `evidence/metrics/runs/` 의 20260722_231246 / A_production / A2_prod_20260804 /
C2_sync30_20260804 / baseline_sync30_20260805 (각 300 s window).

---

## 1. throughput은 딱 한 곳에서 정해진다

**`vitis_ai_detector_node.worker_loop`** — 워커 스레드 1개. 프레임을 워커 프로세스로 넘기고
결과를 기다리므로 한 번에 한 장만 흐른다. 상류는 큐를 쌓지 않고 **덮어쓰며 버리고**
(`latest_msg`), 하류는 전부 이보다 훨씬 빠르다.

### 정확한 규칙

```
period = ┌ 컬러 공급 간격      33.3 ms  (설정된 센서 주기 = 하한)
         │ 직렬 단계 처리시간   43.2 ms  (detector worker)
         └ 명시적 게이트        45.0 ms  (process_period_sec)
           셋 중 최댓값을 → 컬러 도착 격자(33.3 ms)로 "올림"
```

마지막 "올림"이 핵심이다. 게이트에 걸린 프레임은 **버려지고**, 워커는 다음 프레임이
도착할 때까지 대기한다(sleep 아님, `frame_event.wait()`). 그래서 45 ms 게이트는
45 ms 주기가 아니라 **66.7 ms 주기(=2프레임)**를 만든다.

### latency와 혼동하지 말 것

throughput을 정하는 건 각 단계의 **service time(점유 시간)**이지 **latency**가 아니다.
latency = 줄서기 + 작업이고, 줄서기는 다음 프레임을 막지 않는다.
2026-07-31 align 실험이 이 함정의 교과서적 사례다: age_in 298 ms 중 실제 작업은 64 ms뿐이라
latency는 3.1배 나빠졌는데 throughput은 16%만 떨어졌다
(`evidence/metrics/runs/ab_compare_20260731.md`).

## 3. 병목이 **아닌** 것들 (여기부터 손대지 말 것)

### 카메라 — 여유 2배

detector에 **초당 29.4프레임이 도착**하는데 파이프라인은 15.3 Hz만 낸다
(A2/C2 yield: arrived 9287/9302 / 316 s). 공급은 소비의 거의 2배다.

> ⚠️ CLAUDE.md와 `workflow.md` §3.6에 "throughput 천장은 카메라 공급률"이라고 적혀 있던
> 것은 **align이 켜져 있던 시절(카메라가 12 Hz로 throttle)의 사실**이다. 2026-07-14에
> align을 제거한 뒤로는 성립하지 않는다. "모든 소프트웨어 상한을 걷어낸 뒤의 **최종** 천장"
> 이라는 뜻으로는 지금도 맞다(§4의 3단계에서 실제로 여기에 닿는다).

### DPU — 73% 유휴

DPU 추론은 17.7 ms이고 주기는 62.9 ms → **점유율 28%**. DPU만의 이론 한계는
1/17.7 ms ≈ **56 Hz**로 현재의 3.7배다. `xdputil query`가 "DPU Core Count: 2"로 보고하지만
**실제 DPU는 1개**다 — 두 번째 CU는 `pp_pipeline_accel`(전처리 가속 IP, `DPU Arch` 비어 있음)
이고 우리는 쓰지 않는다(§4 4단계).

### CPU — 여유 절반 이상

`isolcpus=3`이라 비전이 쓸 수 있는 건 **3코어**(CPU3은 RT 전용, **절대 쓰지 말 것**).
현재 1.41코어 사용 → 여유 1.59코어.

## 4. 올리는 방법 — 이 순서로 제안할 것

### 0단계(선행): 이건 성능 문제가 아니라 **결정** 문제다

15 Hz는 **의도된 상한**이다. `vitis_ai_detector.yaml`의 주석이 근거를 남겨두었다:
uncapped 시 ~19 Hz였는데 "절약한 CPU를 하류 프레임에 그냥 쓰는 것"이라 판단해
Gate6 목표인 15 Hz로 고정했고, 0.062는 지터로 3프레임 cadence(13.8 Hz)로 튀어서
**0.045로 2프레임 cadence를 잠갔다.**

그 전제는 **정적 물체**였다. 2026-08-04에 움직이는 물체 추종으로 방향이 바뀌었으므로
전제가 달라졌다 — 갱신 주기가 추종 품질에 직결된다. 따라서 아래는 "버그 수정"이 아니라
**상한 재결정**으로 제안해야 한다.

### 1단계: 게이트 완화 — 설정 한 줄, 15.3 → ~23 Hz

`process_period_sec: 0.045` → `0.030` (또는 `0.0`으로 완전 해제).
처리시간 43.2 ms가 이미 30 ms보다 크므로 게이트는 항상 통과 상태가 되고,
주기 = 처리시간 = 43.2 ms → **~23 Hz**. 0.030을 남기는 이유는 향후 처리시간이
33 ms 밑으로 내려갈 때 3프레임 cadence로 튀는 것을 막는 안전 여유.

**⚠️ 2026-08-05 실측 결과 — 공짜가 아니었다.** 같은 장면 back-to-back A/B
(`gate045_rerun` vs `gate030_rerun`, 검출수 5.00/5.00; 3물체 장면 재확인
`baseline_sync30` vs `gate030`):

| | 0.045 | 0.030 | 비고 |
|---|---|---|---|
| throughput | 15.8 Hz | **18.4 Hz** (+16%) | 3물체 장면에선 20.9 Hz — 처리시간에 비례 |
| E2E p50 | **114.4 ms** | 128.2 ms (+14) | 0.030이 나쁨 |
| E2E p95 / p99 | 153.1 / 177.3 | 154.0 / **170.3** | 꼬리는 0.030이 근소 우세 |
| 신선도 p50 (E2E+주기/2) | **146.0 ms** | 155.4 ms | |
| 신선도 p95 | 184.8 ms | **181.2 ms** | |
| CPU 합 | 1.48 | 1.60 (+0.12) | 예상(+0.5)보다 훨씬 쌈 |
| gate_skip / overwritten | 23% / 19% | 0% / **35%** | 메커니즘의 직접 증거 |

E2E가 나빠지는 원인: 게이트가 걸리면 워커는 프레임을 **버리고 방금 도착한 새것**을
집는다(격자 정렬 = 신선한 시작). 게이트를 풀면 처리가 끝나는 즉시 `latest_msg`에
**앉아 있던**(최대 33 ms 묵은) 프레임을 집는다. 직렬 워커의 처리시간이 프레임
주기(33.3 ms)보다 긴 한 **rate와 freshness는 구조적으로 맞바꿈**이며, 게이트는
그 손잡이일 뿐 둘 다 개선하지 못한다.

- 판정: **거의 무승부** — 중앙값 신선도는 0.045, 처리량·꼬리·지터는 0.030 우세.
  이동 물체 추종에선 갱신률·꼬리가 더 중요하다는 판단으로 **0.030 유지(2026-08-05)**.
  정적 pick 위주로 돌아가면 0.045 복귀가 맞다.
- **반드시 A/B로 검증**: `bash tools/metrics/ab_one_run.sh <label>` 두 번(6분).
  단일 런 비교는 장면(검출 수)이 처리시간을 바꿔 오염된다(§`runs/C_sync30`의 함정).

### 2단계: 처리시간을 33.3 ms 아래로 — 1단계의 트레이드오프가 **소멸**하는 유일한 길

처리시간이 프레임 주기(33.3 ms) 밑으로 내려가는 순간 워커는 항상 다음 도착을
**기다리게** 되어, 묵은 프레임 문제(위 +14 ms)가 사라지고 rate는 카메라 상한(30 Hz)에
붙는다. 즉 1단계에서 확인된 "rate ↔ freshness 맞바꿈"을 해소하는 방법은 이것뿐이다.

경로(싼 것부터):
- 방법 0: **IPC 절감 — ✅ 적용·실측 완료(2026-08-05, `shm_frame.py`)**. 프레임을
  stdin pipe(복사 3~4회) 대신 /dev/shm mmap(memcpy 1회)으로 전달. 같은 장면
  back-to-back (`gate030_rerun` vs `shm_gate030`, gate 0.030, 검출 5.00/5.00):
  ipc 13.4→**4.65 ms**, processing 53.0→**44.9 ms**, throughput 18.4→**21.7 Hz**,
  E2E p50/p95 −10/−11 ms, 신선도 p50/p95 −14/−16 ms, **CPU 변화 0**(1.60 — 없앤
  복사만큼 프레임을 더 처리), worker restart/timeout/slow/empty 전부 0.
  이로써 **0.030+shm이 구 기본값 0.045를 전 지표에서 지배**(신선도 p50 141 vs 146,
  p95 166 vs 185, rate 21.7 vs 15.8) — 1단계의 rate↔freshness 맞바꿈이 사실상 해소.
  폴백: `worker_shm: false`. 잔여 ipc ~4.6 ms = JSON 왕복+웨이크업+memcpy.
- 방법 A(권장): **한 워커 안에서 파이프라이닝** — 프레임 N의 전처리를 N−1의 DPU
  추론(17.7 ms)과 겹침. 주기 = max(DPU, CPU분) → ~30 ms 부근. 프로세스가 안 늘어
  위험이 작다.
- 방법 B: 워커 프로세스 2개. DPU는 XRT가 중재하지만 아래 위험이 붙는다.
- 위험(방법 A·B 공통):
  1. **VART 안정성** — 워커를 별도 프로세스로 뺀 이유 자체가 `execute_async` segfault였다.
     러너를 늘리는 건 그 지뢰밭을 다시 밟는 것. 장시간 스트레스 테스트 필수.
  2. **순서 역전** — 워커 2개면 프레임 N+1이 N보다 먼저 끝나 **오래된 검출이 새 것을
     덮어쓸 수 있다.** 하류에 단조 증가 가드 필요.
  3. `dpu_ms` 17.7 ms가 순수 DPU 점유인지 불확실(큐잉·DMA 포함). 실제 겹침 이득은 재봐야 안다.

### 3단계: 카메라 공급 상향 — 30 Hz 이상이 필요할 때만

여기까지 와야 비로소 카메라가 천장이 된다. color fps를 올리는 문제이고
**USB 대역폭**이 따라 오른다. 이 보드는 RealSense USB가 뻗은 이력이 있다
(`-32 STALL`, FW 5.16 RGB 웨지). 30/30+sync로 이미 48.8 → 61 MB/s로 올린 상태라
누적 안정성 근거가 얇다(§`evidence/metrics/runs/sync30_compare_20260804.md`).

### 4단계: 놀고 있는 PL 전처리 가속기

`pp_pipeline_accel`이 PL에 물리적으로 있는데 전혀 안 쓴다. `pre_ms` 8.9 ms(Python LUT)를
하드웨어로 넘기면 CPU분이 ~25 → ~16 ms로 줄어 **병렬 워커 없이도** 2단계 효과가 난다.
다만 VVAS/xfOpenCV 경로를 새로 붙여야 해서 난이도가 가장 높다.
