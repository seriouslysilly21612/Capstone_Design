# A/C 실측: depth 15fps+비동기 vs depth 30fps+sync (2026-08-04)

"align은 빼고, color·depth 둘 다 30fps + `enable_sync`만 켜면 CPU가 얼마나 오르나?
그러면 skew가 B(align)처럼 0이 되나?" 를 확인한 실험.

| | **A2_prod** | **C2_sync30** |
|---|---|---|
| 카메라 | color 30 / depth **15** / sync **off** | color 30 / depth **30** / sync **on** |
| align | off | off (양쪽 동일) |
| 3D 방식 | 단일점 reverse projection (양쪽 동일) | 〃 |

각 300초, **back-to-back 연속 실행**(같은 장면·같은 보드 상태), 뷰어 OFF, 로봇 앱 OFF.
장면 동일성 검증: 프레임당 검출수 **4.62 vs 4.54** (차이 1.7% = 간헐 검출되는 물체 1개).

> 첫 시도(`C_sync30_20260804` vs `A_production`)는 **장면이 달라(검출 5개 vs 1개) 무효**였다.
> 물체 수가 처리시간을 48→40 ms 로 바꾸고, 그게 detector 의 45 ms 게이트를 구속조건으로
> 만들어 throughput 을 17→15 Hz 로 스냅시켰다 — 설정 효과로 오인하기 쉬운 함정.

## 해석

- **skew 0 은 진짜다.** 89% 가 소수점까지 정확히 0.0, 나머지는 정확히 ±33.3 ms(=30 fps 주기)
  배수. sync 가 짝을 만들고 그 짝이 같은 timestamp 를 갖는다는 것이 실측으로 확인됐다.
- **단, sync 만으로는 안 된다.** 같은 런의 `skew_if_latest_ms`(옛 '최신 depth 집기' 정책이면
  나왔을 값)는 p50 33.3 / 평균 34.2 ms 였다. **짝을 만드는 건 sync, 그 짝을 실제로 고르는 건
  2026-08-04 의 최근접 선택 변경** — 둘이 맞물려야 0 이 된다.
- **레이턴시·처리량 비용 없음.** syncer 가 짝을 기다리며 지연을 넣을 것이라는 우려는 기각:
  E2E p50 +1.8 ms(런 간 노이즈 수준), throughput 동일.
  ⚠️ 단 이번엔 양쪽 다 처리시간(41.6/42.3 ms)이 `process_period_sec: 0.045` 게이트 아래라
  **throughput 이 15.2 Hz 로 고정** — 이 실험은 그보다 작은 처리량 차이를 분해하지 못한다.
- **CPU +0.183 코어** = 4코어 보드의 +4.6%p. 사전 추정(+0.15) 과 일치.
- **USB**: 상향 대역폭(depth 12.2→24.4 MB/s)으로 300초×2 런 동안 STALL/웨지 없음,
  `depth_valid_rate 1.0`, worker 타임아웃·재시작 0. 다만 **누적 근거는 ~10분뿐**이다
  (과거 웨지는 더 낮은 대역폭에서도 났으므로 대역폭이 원인이라는 증거는 없다).

## 결론 — 채택 가능하지만 지금 필요하지는 않음

비용은 확인됐고 감당 가능하다(+0.18 코어, 레이턴시·처리량 0). 얻는 것도 진짜다(skew 실질 제거).
그러나 **정지 pick 장면에서 skew 는 z 에 영향이 0**이고, 실시간 추적 캡 0.20 m/s 에서도
최대 6.7 mm→0 인데 접근 오차 6.9~10.7 mm 는 캘리브 편향·마찰이 지배한다. 즉 **묻힌다.**

→ **실시간 추적('o')에서 움직이는 물체를 본격적으로 다룰 때 켠다.** 그때 필요한 것은
`realsense_pick_place.yaml` 2줄(`enable_sync: true`, `depth_profile: 848x480x30`)뿐이다.
